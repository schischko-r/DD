# DDI Editorial · дизайн-система

Версия **0.1.0** · 18 ноября 2026 · [Визуальный каталог](index.html) · [Изменения](CHANGELOG.md)

Система для автономных аналитических HTML-документов и продуктовых страниц DDI: «Клиентский цикл», опрос ОСАГО и CJHUB. Она фиксирует выбранный в этих страницах стиль и поведение повторяющихся элементов. Это локальная система проекта, а не официальный брендбук Сбера или GigaCode.

Существующее React-приложение `gravity-app/` использует Gravity UI. Эта система не меняет его тему и не распространяется на него автоматически. Уже выданные пользователю HTML также не переписываются при сборке каталога.

## С чего начать

1. Откройте [каталог](index.html): в нём живые примеры, состояния и образец диалога CJHUB.
2. Найдите нужный паттерн в [реестре компонентов](components.json), проверьте его контракт и исходный пример.
3. Для новой страницы используйте готовый [ddi.css](ddi.css). Сначала ищите существующий компонент и семантический токен, затем добавляйте новый.
4. Перед изменением прочитайте раздел «Как вести систему». Обновляйте правило, пример и реализацию вместе.

## Зафиксированное направление

Пользователь читает продуктовый или аналитический документ, выбирает контекст, оценивает состояние и переходит к действию. Поэтому ведут содержание, цифры и схема процесса; навигация и оформление им помогают.

- Белый фон, тёмный сине-серый текст, тонкие спокойные границы, минимум декоративных поверхностей.
- Крупные редакционные заголовки Georgia; основной текст и элементы управления — системный sans-serif.
- Синий обозначает действие и выбранный раздел. Зелёный `#139487` — индикатор подтверждения. Фиолетовый — роль агента. Цвет обязательно поддерживается текстом или формой.
- Плотные связанные группы и заметные промежутки между разделами. Нет обязательных экранов `100vh`, принудительного scroll-snap и искусственно пустых экранов.
- Поверхности различаются фоном и тонкой границей. Большие тени, стекло, декоративные градиенты не входят в выбранный стиль.
- Пиктограммы — встроенные линейные SVG. В интерфейсе нет эмоджи. Размер SVG рядом с заголовком связан с размером шрифта, а не зафиксирован на маленьких 16px.
- Схема объясняет процесс картинками: блоки, стрелки, JSON-символ, воронка. Список действий не заменяет графику в утверждённом диалоге CJHUB.
- Каждое действие работает, каждое состояние объяснимо. Галочка не означает «планируем», пустое значение не означает ноль. Способ подтверждения задаёт контракт пункта: ссылка, ручная отметка или проверенный источник.

## Основа: токены и измерения

### Цвет

В JSON есть два слоя: исходные значения `primitive.color.*` и роли `color.*`. Компоненты используют роли, например `--ddi-color-text-primary`, а не произвольный hex.

| Роль | Базовое значение | Применение |
| --- | --- | --- |
| Основной текст | `#16283b` | Содержание, значения, подписи ключевых шагов |
| Вторичный текст | `#657486` | Описание, метаданные и пояснения |
| Белая / лёгкая поверхность | `#ffffff` / `#f7f9fd` | Страница и карточки диалога |
| Декоративная граница | `#e9edf2` | Разделение содержимого; не единственный признак активного поля |
| Граница поля / неактивный текст | `#7b8796` | Контур поля; действительно неактивные состояния |
| Действие | `#2858d9`, hover `#224bc0` | Ссылки, основная кнопка, focus |
| Подтверждение: индикатор / текст | `#139487` / `#0b756b` | Галочка или точка / читаемая подпись |
| Агент | `#7c3aed` | Роль агента, контур и лёгкая подложка блока обработки |
| Внимание: индикатор / текст | `#a77912` / `#805600` | Предупреждение с текстовым статусом |
| Ошибка: индикатор / текст | `#bf514b` / `#a53c37` | Отрицательный статус и его пояснение |

Исходные HTML содержали мелкие подписи `#7b8796` и зелёные подписи `#139487`. На белом их контраст примерно 3.65:1 и 3.74:1 — ниже требования 4.5:1 для обычного текста. Поэтому значения сохранены как исходные акценты, но читаемые метаданные в системе используют `#657486`, а текст подтверждения — `#0b756b`. Старые документы не мигрированы автоматически.

Фиолетовый — принятое локальное обозначение агента, не утверждение об официальном токене бренда GigaCode. Светофорные пороги относятся к методике конкретного продукта; их нельзя зашивать в цветовые токены.

### Типографика

| Уровень | Размер / интерлиньяж | Правило |
| --- | --- | --- |
| Главный заголовок | 40–60px / 1.08, Georgia | На узком экране допускается 36px; переносить, не обрезать |
| Заголовок раздела | 32–44px / 1.12, Georgia | Отрицательный трекинг, один смысловой акцент |
| Заголовок компонента | 16–20px / 1.5, sans-serif | Вес 500–600; не конкурирует с заголовком раздела |
| Основной текст | 14px / 1.6 | Для плотного табличного образца 12px / 1.5 |
| Подпись / значение в компактном блоке | 12px / 1.5 | Включая таблицу на телефоне |
| Необязательная микро-метка | 10px / 1.5 | Только второстепенное содержание; не единственная подпись поля или состояния |

Числа в таблицах и метриках — `font-variant-numeric: tabular-nums`. Иерархия строится размером, весом, цветом и отступом вместе. Увеличение важности не означает увеличение каждого текста. Системные шрифты сохраняют автономность файла.

### Геометрия

- Основа отступов — 4px: `4, 8, 12, 16, 20, 24, 28, 32, 40, 48, 56, 64`.
- Контроль по умолчанию — 44px по высоте; компактный вариант — 40px. У маленькой иконки сохраняется удобная область действия.
- Радиус кнопки, поля и карточки — 4px; диалога — 8px. Другая форма требует отдельного решения, а не случайной правки.
- Контент — до 1120px. Область боковой навигации — 216px; пункты компактные, без пустот между этапами.
- Поля страницы: 48px; до 1100px — 28px; до 760px — 20px; от 1600px — 64px.
- Шапка — 80px, на телефоне — 64px. Мобильное меню под ней — около 61px. Якоря учитывают суммарную высоту закреплённых элементов.
- Схемы перестраиваются или прокручиваются внутри собственной области. Масштабирование не увеличивает документ сверх ширины окна. Заголовки не прячутся через `overflow:hidden`.

Исходные размеры — база для переиспользования, а не требование копировать всю старую страницу. Например, у большого клиентского цикла и небольшого диалога агента разная плотность.

## Компоненты и паттерны

Полный машинный контракт: [components.json](components.json). Нужное поведение важнее сходства одного скриншота.

| Компонент | Основное правило |
| --- | --- |
| Навигация | Текущий раздел, компактные пункты, sticky-offset; на телефоне одна горизонтальная строка |
| Кнопка / ссылка | Настоящие button / a, понятное действие, focus / hover / disabled; SVG вместо эмоджи |
| Продуктовый фильтр | Выбор «Вклады» / «Прайм» меняет контекст, остаётся доступным при прокрутке |
| Чеклист с подтверждением ссылкой | До ссылки галочка снята; после — «Перейти →» под пунктом; другие способы подтверждения описываются явно |
| Числовое поле | Пробелы в тысячах; единица справа внутри поля; редактирование без скачущего курсора |
| Поле с источником | Источник указан; подтверждённое значение серое и readonly; ручное редактируемое |
| Светофор + вывод | Один статус управляет цветом, текстом светофора и пояснением; unknown не равен red |
| Таблица | Семантическая разметка, выровненные числа, читаемость на 320px, «—» для отсутствия данных |
| Диалог агента | Запрос → стрелка → отдельный блок агента с графикой → стрелка → ответ-таблица |
| Клиентский путь | Смысловой порядок, читаемые узлы и связи; легенда и масштаб при необходимости |
| Аналитическое пояснение | Факт, рекомендация и источник различимы; никаких выдуманных эффектов |
| Вкладки | Одна активная панель, корректный фокус, стрелки / Home / End и ARIA-связи |
| Навыки | Название, инструмент, назначение; details/summary для подробностей |

### Особо важное решение: диалог CJHUB

Сохранить три визуально самостоятельные стадии:

1. **Запрос пользователя** — спокойная карточка с текстом запроса.
2. **«Агент думает»** — фиолетовая подложка и рамка; внутри крупные `{ }` / JSON-спецификация → стрелка → мини-воронка из трёх сужающихся полос. Подписи краткие, графика заметная.
3. **Ответ агента** — карточка в стиле запроса, внутри таблица «Шаг / Клиенты / Конверсия / Среднее время».

Стрелки есть перед блоком агента и после него. Горизонтальный разделитель не заменяет стрелку. Уменьшать высоту можно за счёт отступов и повторяющихся пояснений; нельзя ради компактности удалять стадию агента или заменять её списком действий. Это статичный пример процесса, не имитация выполняющегося расчёта и не публикация внутренних рассуждений модели.

Три строки мини-воронки показывают форму сценария, а не реальные доли клиентов. В примере таблицы числовые ячейки — `—`; результаты пилота и вымышленные конверсии не подставляются.

### Данные и источники

`readonly`-значение с источником можно выделить и скопировать. Оно не становится disabled и не теряет читаемый цвет. Указание источника — происхождение значения, а не декоративный бейдж: веб-ссылка либо название документа и точный локатор, если источник локальный.

В варианте чеклиста с веб-ссылкой принимаются только валидные HTTP(S)-ссылки. Пока их нет, отсутствует и подтверждающая галочка. Удаление ссылки снимает подтверждение. Валидность адреса сама по себе не проверяет качество содержимого: если задаче нужна экспертная валидация, она остаётся отдельным условием.

Это не универсальный запрет на ручные чекбоксы. В клиентском цикле уже согласованы исключения: «Построить помесячно воронку» (`monthly`) отмечается вручную без ссылки, а проверенное значение из источника может прийти со статусом и быть заблокировано для изменения. Источником может быть локальный документ с названием и локатором без веб-URL. Эти варианты должны быть заданы явно в данных/контракте пункта; нельзя ни стирать их общим URL-правилом, ни самовольно объявлять любое отсутствие ссылки подтверждением. Статусы согласованной методики TAM/SAM также задаются предметными данными.

Недоступный источник и пустые данные отображаются явно; автоматически менять их на ноль или зелёный статус нельзя.

Форматирование числа и хранение значения — разные операции. Для ввода используется текстовое поле с подходящим `inputmode`; единица живёт отдельным элементом внутри обёртки и входит в доступное описание. Не вставлять единицу в числовое значение. Пример форматирования — `1 250 000`.

Нельзя придумывать источник, факт, достижение пилота или причинную связь. Технические подробности появляются только там, где помогают принять решение.

## Доступность и состояния

- Обычный текст: контраст не ниже 4.5:1; крупный — 3:1. Значимые контуры, focus и графические сигналы — 3:1 там, где они нужны для распознавания. Тонкая декоративная граница карточки не обязана сама передавать её смысл.
- Цвет состояния сопровождается словами и при необходимости иконкой. Светофор без подписи недостаточен.
- Нативные `button`, `a`, `select`, `input`, `details`, `table`; видимый focus; клавиатурные сценарии для вкладок. У каждого поля — label; у ошибки — связь с полем.
- Наш стандарт высоты действий — 44px. Это локальный комфортный выбор: WCAG 2.2 AA для 2.5.8 задаёт 24×24px с исключениями, а не универсальные обязательные 44×44px.
- Проверять 320, 390, 1280 и 1440 CSS px, увеличение текста/масштаба и длинные русские подписи. Не рвать слова ради того, чтобы втиснуть таблицу; сокращение имеет полное доступное имя.
- Учитывать `prefers-reduced-motion`. Нет постоянного мерцания, автопрокрутки и псевдоиндикатора живой работы в статичной иллюстрации.
- Для каждого компонента перечислить нужные состояния: default, focus, disabled, empty, invalid, readonly, linked и другие по его задаче. Не добавлять фальшивые интерактивные состояния к декоративной картинке.

Автотесты проверяют выбранные контрастные пары и поведение примеров. Это не полная сертификация WCAG, не исследование со всеми пользователями и не проверка всех браузеров. Каталог служит проверяемой базой; новые применения требуют проверки в их контексте.

## Как вести систему

### Роли и статусы

Владелец задачи задаёт потребность и визуальные ограничения. Frontend сопровождает реализацию, tester — проверки, reviewer независимо принимает результат. Именной постоянный сопровождающий системы не назначен этим документом; его следует указать в задаче, когда такая роль появится.

Статусы реестра:

- `candidate` — предложение с описанием потребности и примером; ещё не общий стандарт.
- `documented` — решение зафиксировано из текущих страниц, имеет контракт и локальный пример. Это статус первой версии, а не заявление о широкой проверке в продакшене.
- `deprecated` — не использовать в новых работах; указаны замена и способ миграции.

Это локальный процесс, вдохновлённый практикой дизайн-систем; статусы не являются утверждением об участии DDI в GOV.UK.

### Изменение в одном наборе правок

1. **Потребность.** Что сейчас не получается у пользователя? Где встречается повторение? Найти существующий компонент, чтобы не создать его копию.
2. **Контракт.** Указать роль, состояния, ограничения, пример и влияние на прежние страницы. Новое одноразовое решение сначала `candidate`.
3. **Источник.** Цвет/размер менять в `tokens.json`; разметку — в шаблоне; стили — в `components.css`; поведение — в `catalog.js`. Нельзя вручную чинить только сгенерированный каталог.
4. **Документация.** Обновить `components.json`, пример каталога и при необходимости это руководство; добавить запись в CHANGELOG с причиной и миграцией.
5. **Версия.** Увеличить версию в `$extensions.org.dddev.design-system.version`, собрать производные файлы. Метка версии в каталоге подставляется из того же JSON.
6. **Проверка.** Сборка, `--check`, релевантные тесты, визуальная проверка нужных ширин и клавиатуры. Проверять реальную CSS-ширину окна, а не только значение эмулятора.
7. **Приёмка.** Независимый reviewer возвращает APPROVED или необходимые исправления. Обычные правки внутри уже согласованной задачи не требуют нового запроса разрешения пользователя. Commit и push выполняются только по явному запросу, как требует AGENTS.md.

### Версии и миграции

Публичный контракт системы — имена CSS-токенов, классы `.ddi-*`, состояния компонентов и их семантика. До 1.0 API ещё формируется: несовместимое изменение в 0.x повышает minor и обязательно описывается как несовместимое. После 1.0 несовместимая правка повышает major; совместимый новый компонент — minor; совместимое исправление — patch. У опубликованной версии не заменяют молча содержимое.

Изменение или удаление токена/класса сопровождается таблицей «старое → новое» и перечнем затронутых потребителей. Старый вариант сначала помечается deprecated, если его используют другие страницы. Новая система не является поводом массово менять ранее выданные HTML без задачи на миграцию.

Шаблон записи решения:

```text
Потребность: какая задача пользователя не решалась
Решение: компонент/токен и его контракт
Основание: ссылка на исходную страницу или обратную связь
Состояния: default / ...
Совместимость: что меняется у потребителей
Проверки: команды, ширины, клавиатура, ограничения
Версия и миграция: X.Y.Z, старое → новое
```

### Почему пока без Storybook и отдельного npm-пакета

У текущих документов автономный HTML и нативные элементы, поэтому достаточно общего CSS, исполняемых примеров и детерминированной сборки. Storybook полезен, когда появится общая компонентная библиотека приложения с несколькими потребителями; его не нужно устанавливать ради одного каталога. Связка примера, контракта и состояния сохранена и без него.

Figma-библиотека может стать дополнительным представлением тех же токенов. До реальной синхронизации она не объявляется вторым источником истины и не считается уже существующей.

## Что взято из внешних рекомендаций

Проверено 18 ноября 2026. Ниже — основания устройства системы, не заимствованный визуальный стиль.

- **Единый формат токенов.** DTCG 2025.10 описывает JSON-токены, типы и ссылки между ними. Здесь использован небольшой набор: `color` sRGB, `dimension`, `number`, `fontFamily`, `fontWeight`, `duration` и ссылки на целое значение. Сборщик не является полным валидатором DTCG: `$extends`, JSON Pointer, составные типы и другие цветовые пространства не поддерживает. Документ DTCG — Community Group Report, не стандарт W3C. [DTCG Format 2025.10](https://www.designtokens.org/TR/2025.10/format/)
- **Ограниченная палитра решений.** USWDS использует токены для согласованных цветов, размеров и типографики. Отсюда принцип небольшого набора значений и семантических ролей. [USWDS Design tokens](https://designsystem.digital.gov/design-tokens/)
- **Потребность, повторное использование и проверка.** GOV.UK оценивает полезность и уникальность предложения, затем удобство, согласованность и применимость реализации. Это основание нашего контракта изменения и независимой приёмки. [GOV.UK Contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/)
- **Уровень готовности должен быть виден.** Статус компонента помогает понять, насколько решение проверено и может ли меняться. Наши статусы адаптированы к локальной базе 0.1. [GOV.UK Component lifecycle](https://design-system.service.gov.uk/community/component-lifecycle-statuses/)
- **Примеры рядом с документацией.** Storybook связывает истории компонентов с документацией и метаданными. Здесь та же идея реализована простым каталогом, без установки фреймворка. [Storybook: documenting components](https://storybook.js.org/docs/writing-docs)
- **Проверяемая доступность.** Численные требования к контрасту и размерам целей взяты из W3C, а не из визуального вкуса. [WCAG Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), [Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- **Явная совместимость версий.** Номер версии сообщает об исправлении, расширении или несовместимом изменении контракта. Правило для периода 0.x описано выше отдельно. [Semantic Versioning](https://semver.org/)
