# Объединённый отчёт по черновикам и воронке

`build_report.py` собирает автономный HTML из двух экспортов и локального
отчёта LossHunter:

- черновики по продуктам;
- кликстрим по воронкам, этапам, событиям и NRT;
- рекомендации по коммуникациям для пути «Купить ОСАГО · СберБанк Онлайн · ios».

За один запуск создаются две версии отчёта:

- `report_merge_funnel_drafts.html` — аналитическая;
- `report_merge_funnel_drafts_copy_paste.html` — те же данные и основной
  читательский блок рекомендаций LossHunter. Секция
  `<section class="block-section section-filter_table">` переносится без
  пересборки текста или разметки.

Обе версии сохраняются в текущей папке и зеркалируются в корень репозитория.
Корневые файлы подключены к локальному DDI через `/.env.example` как пункты
«Черновики и оформление в СБОЛ» и «Коммуникации · copy-paste».

Продуктовый навигатор строится из канонической линейки DDI в
`gravity-app/public/report-data.json`: берутся только записи типа `Продукт`.
В текущем источнике это 64 продукта. Все строки навигатора кликабельны:
18 продуктов открывают один из 19 собранных отчётов, а для остальных
показывается отдельное состояние с объяснением отсутствия полного среза.
Сегменты и каналы DDI в навигатор не попадают.

Базовые связи читаются из `ai_product_mapping.xlsx` (`drafts` и
`clickstream_funnel`). В `mapping.json` хранится только явное разрешение
many-to-many вариантов и выбор `funnel_id` при повторяющихся именах. Генератор
проверяет каждую выбранную связь по XLSX и не использует fuzzy matching.

## Запуск

Из текущей папки:

```bash
python3.11 build_report.py
```

Без аргументов скрипт ищет исходники в `input/`, корне репозитория,
`~/Documents/Codex/DD-dev` и `~/Downloads`. Пути можно передать явно:

```bash
python3.11 build_report.py \
  --drafts "/path/to/Черновики_все_продукты_zeroed.html" \
  --clickstream "/path/to/Кликстрим_Месячный_все_воронки (1)_zeroed(1).html" \
  --product-mapping "/path/to/ai_product_mapping.xlsx" \
  --ddi-data "/path/to/report-data.json" \
  --losshunter "/path/to/Рекомендации по коммуникациям с брошенными корзинами · Купить ОСАГО · СберБанк Онлайн · ios.htm" \
  --output report_merge_funnel_drafts.html \
  --copy-output report_merge_funnel_drafts_copy_paste.html
```

Для каждого продукта выбирается последний месяц, одновременно присутствующий
в черновиках и кликстриме. В приложенных выгрузках это июнь 2026 года.

`ДСЖ КК` явно указан в `excluded_products`: в черновиках для него есть только
сентябрь 2025 года, а кликстрим начинается с февраля 2026 года, поэтому общего
среза нет. Неоднозначный канонический продукт `ЗЛС` разрешён в пользу общей
воронки «Защита на любой случай»; другие модули можно добавить отдельными
строками конфигурации.

`Вклады+НС` связан с двумя вариантами отчёта — «Вклады, руб.» и
«Накопительные счета». После выбора продукта оба варианта доступны отдельными
кнопками, поэтому ни один из них не теряется.

## Интерфейс DDI

Информационная архитектура построена как реестр покрытия:

1. контекст и поиск продукта;
2. линия `брошенные корзины → коммуникации → доля покрытия`;
3. этапы воронки и сводка NRT;
4. сценарии LossHunter `триггер → событие → канал → сообщение → проверка`;
5. технический маппинг и источники.

Используются DDI-паттерны: светлый generic-фон, плоские аналитические
поверхности с радиусом 8 px, borders-only depth, брендовый синий только для
фокуса и навигации, семантические статусы NRT и компактная типографика.
В zeroed-режиме количественные метрики показываются как обезличенные, а не как
фактические нули. NRT-покрытие остаётся доступно, поскольку рассчитывается по
сопоставлению событий.

События не разворачиваются в длинную строку таблицы: для каждого этапа
показывается компактный счётчик, а реестр event-групп создаётся только при
раскрытии строки. Каждая группа получает явный текстовый статус покрытия.

Навигатор использует стабильный `product.id`, ищет также по алиасам вариантов,
поддерживает клавиатуру, query-параметр `product` и скрытый DDI-адаптер
`#exp-product` / `#exp-period` / `#exp-show`. При встраивании в iframe
standalone-шапка автоматически скрывается.

## Правило покрытия NRT

Для каждой исходной группы событий этапа берётся список
`event_token_groups`. Событие считается покрытым, если `original` из
`nrt_matches` после удаления платформенного префикса (`ios /`, `android /`)
точно совпало хотя бы с одним токеном группы.

- все группы сопоставлены — полное покрытие;
- часть групп сопоставлена — частичное покрытие;
- совпадений нет — покрытие отсутствует.

Числовое поле `matched` не используется, поскольку в zeroed-выгрузке оно
обнулено вместе с метриками.

## Рекомендации

Локальный HTML LossHunter является явным источником рекомендаций. Парсер
извлекает 9 карточек, путь, идентификатор прогона, происхождение значений и план
проверки. Основная читательская часть берётся из исходной таблицы LossHunter
для сочетания по умолчанию `день × 25–60`: срок, основной и запасной канал,
связный текст рекомендации, пример сообщения, up-sell и обоснование. Технические
поля показываются только в раскрываемом блоке условий запуска. Для ОСАГО
карточки также переносятся дословно по смысловым полям:
`Триггер`, `Событие в реестре`, `Сегмент`, `Время отправки`, каналы, текст,
up-sell, обоснование, метрика и шаблон ТЗ.

Источник построен по одному пути ОСАГО и анкете владельца. Поэтому для других
продуктов факты ОСАГО не переиспользуются: отчёт показывает только структуру ТЗ
LossHunter и помечает продуктовые поля как `нужен ввод`. Технические этапы
кликстрима не считаются автоматически равными этапам CJX; перед запуском нужен
явный маппинг на реестр событий NRT/CJ. Маркеры источника сохраняют исходный
смысл: `· путь`, `· анкета`, `· гипотеза`, `нужен ввод`.

В copy-paste версии рекомендации не строятся из отдельных полей. Генератор
забирает из входного LossHunter HTML основной блок «Клиент оборвал на этапе —
что, когда и куда отправлять» (`section-filter_table`) и хранит его как исходную
строку. На странице этот HTML вставляется напрямую, а кнопка кладёт в буфер
одновременно `text/html` и текстовое представление. Тест сравнивает блок с
входным HTML на полное строковое равенство.

Расположенная ниже техническая секция «Заготовка ТЗ на коммуникацию»
(`section-details`, карточки `details.dt-item`) в copy-paste версию не входит.

Для других продуктов исходных карточек во входных HTML нет. Поэтому
copy-paste версия не генерирует для них замену или шаблон, а явно сообщает об
отсутствии исходного блока.
